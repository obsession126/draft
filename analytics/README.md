# Аналітичний модуль

Модуль запускає повністю синтетичне джерело телеметрії, формує узгоджені вектори вимірів, оцінює їх відносно синтетичного базлайну й надає результат локальному фронтенду через JSON API та Server-Sent Events (SSE). Фізичні датчики, база даних і медично валідована модель не потрібні. Історія обмежена останніми 500 подіями в пам'яті процесу; після перезапуску вона очищується.

## Запуск

З кореня репозиторію у Windows PowerShell:

```powershell
python -m venv analytics\.venv
.\analytics\.venv\Scripts\python.exe -m pip install -r analytics\requirements.txt
.\analytics\.venv\Scripts\python.exe -m analytics
```

Сервіс слухає лише `127.0.0.1:8765` за замовчуванням. Після старту він формує синтетичний базлайн і запускає симулятор зі швидкістю одна подія на секунду. Для наочнішого/повільнішого потоку можна змінити інтервал і зерно генератора:

```powershell
.\analytics\.venv\Scripts\python.exe -m analytics --interval 2 --seed 42 --scenario demo
```

Доступні режими: `demo`, `normal`, `interaction_shift`, `gradual_drift`, `sensor_artifact`, `signal_loss`, `radiation_event`. Режим `demo` повторювано перемикає стабільний базлайн, нелінійну невідповідність між сигналами, артефакт/низьку якість, дрейф, втрату сигналу та радіаційну подію. Сценарій є міткою тестового симулятора, не передається моделі як ознака й не є клінічною міткою.

Локальний клієнт Next.js може читати API з `http://127.0.0.1:8765`. За потреби дозволені браузерні origins змінюються через `ANALYTICS_CORS_ORIGINS` (перелік через кому). Не виставляти демонстраційний сервер у публічну мережу без автентифікації, авторизації та належного захисту даних.

Для live-дашборду клієнт може підписатися на SSE:

```typescript
const stream = new EventSource("http://127.0.0.1:8765/api/v1/stream");
stream.addEventListener("telemetry", (message) => {
  const event = JSON.parse((message as MessageEvent<string>).data);
  // Update chart series from event.measured_at and event.measurements.
  // Render event.analysis.status, score, data_quality, and top_contributors.
});
```

Для першого завантаження UI може викликати `GET /api/v1/snapshot`, а для графіків — `GET /api/v1/history?limit=100`. Використовувати `feature_names` + `feature_vector` для моделей/таблиць, або `measurements[name]` для діаграм з підписами й одиницями; `analysis.status` не інтерпретувати як клінічний статус.

## HTTP API

| Метод і шлях | Призначення |
|---|---|
| `GET /healthz` | Перевірка доступності процесу |
| `GET /api/v1/snapshot` | Стан сервісу, лічильник подій і найновіший вимір з аналізом |
| `GET /api/v1/history?limit=100` | Останні виміри; `limit` обмежено діапазоном 1–500 |
| `GET /api/v1/stream` | SSE-події `telemetry`; кожна подія має `id` для відновлення через `Last-Event-ID` |

Формальний JSON Schema для одного telemetry event розташований у [event.schema.json](./event.schema.json). Позиційний масив `feature_vector` визначений парним масивом `feature_names`; порядок є частиною контракту версії `1.0`.

Схематичний фрагмент `snapshot` (скорочення `...` навмисні; повну валідну форму події визначає JSON Schema вище):

```json
{
  "schema_version": "1.0",
  "service": {
    "status": "running",
    "source": "synthetic-simulator",
    "scenario_mode": "demo",
    "analysis_version": "nonlinear-ensemble-v1",
    "calibration": {
      "source": "synthetic-normal-baseline",
      "samples": 768,
      "medical_validation": false
    },
    "started_at": "2026-01-01T00:00:00Z"
  },
  "event_count": 1,
  "latest": {
    "schema_version": "1.0",
    "event_id": "crew-01-00000000",
    "measured_at": "2026-01-01T00:00:00Z",
    "recorded_at": "2026-01-01T00:00:00Z",
    "source": "synthetic-simulator",
    "is_synthetic": true,
    "feature_names": ["hr_bpm", "hrv_ms", "... 34 additional feature names"],
    "feature_vector": [77.1, 50.2, "... 34 additional values"],
    "measurements": {
      "hr_bpm": {
        "value": 77.1,
        "unit": "bpm",
        "quality": "good",
        "source": "simulated"
      },
      "...": "additional measurements follow the event.schema.json contract"
    },
    "context": {
      "profile_id": "crew-01",
      "mission_elapsed_min": 0,
      "mission_phase": "transit",
      "link_online": true,
      "simulation_scenario": "normal"
    },
    "analysis": {
      "status": "normal",
      "score": 0.41,
      "score_kind": "empirical_tail_rank_not_probability",
      "threshold": 0.99,
      "detector": "nonlinear-ensemble-v1",
      "explanation": "Вектор не перевищив демонстраційний поріг відносно синтетичного базлайну.",
      "top_contributors": [],
      "data_quality": {
        "valid_fraction": 1.0,
        "missing_features": [],
        "low_quality_features": [],
        "status": "good"
      }
    }
  }
}
```

Приклад скорочений: у реальній відповіді `feature_names`, `feature_vector` і `measurements` містять усі 36 ознак з реєстру. Позиція кожного значення у `feature_vector` відповідає полю з таким самим індексом у `feature_names`; для діаграм краще використовувати `measurements` за іменем і одиницею. `measured_at` — час симульованого виміру, `recorded_at` — час запису. Відсутні дані представлені `null`, низька якість — `quality: "low"`, втрачений сигнал — `quality: "missing"`.

Стани `analysis.status`:

- `normal` — вектор не перевищив демонстраційний поріг, це не сертифікація нормального стану здоров'я;
- `anomaly_review` — модель побачила нетипову комбінацію, що потребує перегляду;
- `data_quality_review` — є пропуск або низька якість, тому результат не можна показувати як підтверджено нормальний;
- `insufficient_data` — замало валідних ознак; `score` буде `null`.

`score` — емпіричний хвостовий ранг спільного максимуму оцінок Isolation Forest, умовних залишків нелінійних моделей і маргінальних відхилень окремих сигналів, повторно калібрований на відкладених синтетичних прикладах; це не ймовірність, довіра до діагнозу чи універсальна метрика ризику. Накопичена доза використовується у векторі й Isolation Forest, але не оцінюється як ізольований рівень, бо її нормальне значення залежить від часу місії. `threshold` — демонстраційне налаштування, не медичний поріг. `top_contributors` наводить відхилені ознаки та парні взаємодії; `deviation_magnitude` — відхилення в перетвореному просторі ознак, не ймовірність чи причинне пояснення.

## Персональні тренди й XGBoost

DRF profile-insights API формує окрему одно-крокову модель для кожної характеристики з якісної історії профілю. У щойно отриманій історії це окремі події; після запуску `compact_telemetry` старші дані представлені середніми значеннями хвилинних агрегатів. `XGBRegressor` прогнозує наступне спостереження для числових каналів; категоріальні коди можуть використовувати `XGBClassifier`, якщо в історії достатньо прикладів кількох класів. Числова модель навчається на ранніх 80% послідовності, оцінюється на пізнішій хронологічній частині й прогнозує один наступний семпл за останніми вісьмома значеннями та доступним контекстом місії. Ціль — значення наступного виміру, а не медичний стан чи синтетична сценарна мітка. Для числових каналів API повертає напрямок робастного нахилу, прогноз, кількість використаних значень і медіанну абсолютну похибку на хронологічному holdout-відрізку.

Модель вимагає щонайменше 36 якісних вимірів каналу. Це sample-based прогноз на один наступний запис, а не прогноз на певну кількість хвилин/годин. Holdout-похибка описує лише минулі помилки цієї моделі на доступній історії; вона не є ймовірністю, confidence interval або клінічною невизначеністю. Категоріальні значення без варіативності та канали з недостатньою історією не отримують штучний прогноз. Пропущені й низькоякісні значення не входять у навчальну послідовність.

Це експериментальна персональна модель часових рядів, а не доведене покращення точності чи перевага над Apple Watch або іншими медичними/споживчими продуктами. Немає незалежної перевірки на реальній космічній телеметрії. Підготовка, відбір чи рейтинг астронавтів не є ціллю системи; високоставкові рішення про людей потребують окремих валідованих процедур та людського нагляду.

## Параметри вектора

Джерелом порядку, назв, категорій та одиниць є `analytics/contracts.py`; він відповідає [реєстру кандидатних параметрів](./PARAMETER_CATALOG.md). Вектор включає:

- серцево-судинні сигнали: HR, HRV (RMSSD у симуляторі), артеріальний тиск і симульований ECG-derived RR інтервал;
- дихання, SpO₂ та температуру шкіри;
- сон, тип/тривалість/інтенсивність активності, рух і самооцінки категорії/тяжкості симптомів, стресу, настрою та бадьорості;
- дозиметричні значення й умови кабіни: температура, тиск, вологість, освітлення, шум, CO₂, O₂;
- довготривалі/дослідницькі поля, харчування й гідратацію.

Значення з назвами `*_index`, ECG-derived, Lab і OCT — лише синтетичні числові проксі для перевірки потоку даних і взаємодій. Це не реальні клінічні виміри. Сирий ECG, діагностичні пороги, структуровані лабораторні панелі та валідовані OCT результати потребують окремих форматів і джерел.

Поза вектором залишаються ідентифікатори й контекст місії: фаза, EVA, стан зв'язку, подія/контрзахід і мітка сценарію. Їх можна відображати або використовувати для фільтрації та часових пояснень; модель не використовує сценарій чи мітку істини.

## Як працює виявлення

1. На старті генератор створює 768 синтетичних прикладів базового режиму й детерміновано перемішує їх фіксованим seed, щоб усі частини містили різні часові фази симуляції. Половина призначена для умовних моделей, чверть — для Isolation Forest, остання чверть — незалежна чиста калібрувальна вибірка. Вони не містять міток захворювань і не використовуються як доказ медичної валідності.
2. `RobustScaler` нормалізує числові поля з різними одиницями. Окремі випадкові ліси прогнозують очікуваний HR, HRV, частоту дихання, SpO₂ та якість сну з їхнього контексту; умовні залишки оцінюються на окремій частині чистого синтетичного базлайну.
3. `PolynomialFeatures(degree=2)` додає квадрати та попарні перетини ознак, а Isolation Forest оцінює нетиповість повного розширеного вектора відносно синтетичних калібрувальних прикладів. Окремо оцінюється відхилення кожного сигналу; спільний максимум усіх трьох компонентів повторно калібрується за відкладеною вибіркою, щоб контролювати сукупний поріг. Накопичена доза не оцінюється окремо від часу місії. Модель не навчається онлайн на подіях, аби не засвоювати аномальні симуляції як норму.
4. Пояснювальний шар повертає найбільш віддалені одновимірні, парні та умовні ознаки. Якість сигналу оцінюється окремо: ознаки низької якості не використовуються як нормальне значення, а при значних пропусках модель не повертає оцінку.

Цей event-level детектор і profile-level XGBoost trend forecaster — різні шари. Детектор аналізує кожну подію відносно синтетичного базлайну; profile-insights XGBoost прогнозує наступне значення кожного каналу на основі попередньої історії профілю.

Модель виявляє відмінність від обмеженого синтетичного розподілу. Вона не гарантує виявлення всіх прихованих залежностей, не є клінічно навченою й не повинна використовуватись для постановки діагнозу або прийняття рішень про лікування. Градієнтний бустинг для аномалій не використовується: без незалежних валідних міток класифікатор навчився б відтворювати мітки симулятора, а не підтверджувати реальну користь.

## Перевірки

```powershell
.\analytics\.venv\Scripts\python.exe -m unittest discover -s analytics\tests -v
```

Тести перевіряють повноту й порядок контракту, багатовимірний сценарій із порушеною взаємодією, реакцію на якість/пропуски та HTTP-відповіді. Це перевірки програмної поведінки на синтетичних даних, не медична валідація.
