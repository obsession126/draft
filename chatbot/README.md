# Orbital Health Copilot

Ізольований Gemini-адаптер для Health Copilot у головному Next.js інтерфейсі. Сторінка чату знаходиться в `frontend/my-hub/src/app/chat`; Python-сервіс надає лише захищений локальний API і не створює окремий UI.

## Інноваційна відмінність

**Evidence-first, mission-aware copilot** не зводить дані до абстрактного індексу. Для кожної відповіді він підтягує останню телеметрію, якість і свіжість сигналів, персональні базові лінії та висновки звіту; Gemini отримує саме цей актуальний контекст. Відповідь містить джерела, на які посилається, та може показати лише наступні кроки, уже запропоновані звітом. Посилання на NASA додаються окремо від персональних даних.

Аналітичні значення не інтерпретуються як діагноз: оцінка детектора — не ймовірність, зміна від базової лінії — не медичний поріг, а внесок моделі — не причина зміни. Якщо значення відсутнє або має низьку якість, це лишається невідомим, а не «нормою».

## Межі даних і безпеки

- Gemini API key зберігається лише в середовищі локального Python-сервера; браузер його не отримує.
- Чат передає профільні дані до Google AI Studio. Екран входу показує цю інформацію і вимагає підтвердження перед початком роботи. Для презентації використовуйте лише синтетичний профіль.
- Сервер **блокує передачу реальних телеметричних даних**. Підключення реальних вимірів потребуватиме окремого рішення про приватність, захист даних і зовнішню обробку; перемикача для обходу цього захисту в прототипі немає.
- API-токен місії зберігається лише в оперативній пам'яті вкладки та не записується в `localStorage` чи URL. Вихід очищає розмову і токен.
- Сервер слухає лише `127.0.0.1`. Не виставляйте його в публічну мережу.
- Це прототип ситуаційної обізнаності, не медичний пристрій, клінічна система підтримки рішень або заміна бортового лікаря. За серйозних чи раптових симптомів дійте за аварійним протоколом місії та негайно зв'яжіться з медичним фахівцем.

## Запуск локальної презентації

Потрібні Python 3.10+ та запущені Django API і симулятор зі створеним профілем. Якщо `chatbot/.env` ще не існує, створіть його з шаблону та додайте власний ключ (локальний `.env` не потрібно комітити). Із кореня `draft/` у macOS/Linux:

```bash
test -f chatbot/.env || cp chatbot/.env.example chatbot/.env
# Відредагуйте chatbot/.env і встановіть GEMINI_API_KEY
python -m chatbot.server
```

Адаптер читає локальний `chatbot/.env` під час запуску. Значення, задані в середовищі термінала, мають пріоритет. Якщо змінюєте `.env` після запуску, перезапустіть Python-сервіс.

Цей процес слухає лише `127.0.0.1:8766`. У `frontend/my-hub/.env.local` встановіть адресу проксі:

```dotenv
CHATBOT_API_URL=http://127.0.0.1:8766
```

Запустіть Next.js застосунок у `frontend/my-hub` командою `npm run dev`, увійдіть у mission control і перейдіть до **Health copilot**. Токен і вибраний crew profile беруться з чинної сесії основного інтерфейсу; другий вхід чи окремий браузерний чат не потрібні. Gemini model за замовчуванням — `gemini-3.5-flash-lite`, оптимізована для низької затримки та високої пропускної здатності; за потреби встановіть `GEMINI_MODEL` відповідно до моделей, доступних вашому Google AI Studio API key.

Backend API за замовчуванням: `http://127.0.0.1:8000`. Щоб змінити його, встановіть `MISSION_API_BASE_URL`. Google AI Studio key можна створити в [Google AI Studio](https://aistudio.google.com/app/apikey); не додавайте реальний ключ у файли проєкту чи презентаційні матеріали. Шаблон змінних середовища — [.env.example](./.env.example). Python-модуль використовує лише стандартну бібліотеку; додаткові пакети встановлювати не потрібно.

## Потік запиту

1. Користувач входить у Django через основний frontend; Next.js зберігає токен у вкладковій сесії та передає його same-origin route handler лише під час запиту до чату.
2. Next.js проксіює повідомлення в локальний Python service, не відкриваючи Gemini API key у браузері. Сервіс читає `GET /dashboard/` і `GET /insights/?limit=120` під автентифікованим токеном.
3. Gemini отримує поточні виміри, якість, контекст місії, звітні метрики/базлайни, останні 12 точок кожної метрики, висновки та дозволені дії. На виході модель мусить повернути структурований JSON.
4. Сервер перевіряє всі evidence/action IDs проти контексту конкретного запиту. Невідомі ID не показуються як джерела чи рекомендації.
5. Основний frontend показує відповідь, джерела, передбачені звітом дії та стан якості/аналізу. Перемикання профілю очищає чати, щоб не змішувати дані екіпажу.

Цей адаптер відокремлює UI, джерело телеметрії та формування контексту. Якщо контракт аналітики зміниться, достатньо адаптувати `build_grounded_context`; Next.js chat API та інтерфейс залишаються стабільними. Інтерфейс переосмислює загальні патерни чату Open WebUI, не копіюючи його вихідний код.

## Перевірки

Із `draft/`:

```bash
python -m unittest chatbot.tests.test_server -v
python -m py_compile chatbot/server.py chatbot/tests/test_server.py
```

Тести перевіряють перенесення якості/базлайнів у доказовий контекст, відсікання неіснуючих посилань моделі та відхилення порожньої відповіді. Це програмні перевірки, не медична валідація.
